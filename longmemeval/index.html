Measured

I benchmarked my own memory tool. The first result was 16%.

Jay Pitts, Protechtus. 2026-11-24. Sextant on LongMemEval: 500 questions, two reader models, every loss kept in.

Sextant is a memory layer for AI agents. It keeps what you and your assistant have worked out in plain markdown files on your own machine, and lets the assistant look things up instead of starting from zero every session. I built it, I use it every day, and until this month I had never measured it against anything but my own impression that it worked.

So I measured it. LongMemEval is a public benchmark from a 2025 research paper: 500 questions, each about a long chat history, where the answer is buried somewhere in roughly fifty past conversations. I ran Sextant against it, and I ran the comparison I most wanted to see and rarely do: skip the memory tool entirely and paste the whole history into the model.

The first number was 16%.

What was broken

Before spending anything on models I ran the search step by itself, which is free. For 406 of the 470 answerable questions, Sextant returned nothing at all.

The cause was almost embarrassing. Its keyword search required every word of the query to appear in a single note. An agent that writes short keyword queries never trips on that. A person who types a question as a sentence trips on it every time. "What was the first issue I had with my new car after its first service?" matched no note, because no note contains all of those words.

I had shipped that. It had been public for a week.

The fix is small: when no note holds every word, rank notes by the words they share, mark those matches as loose, and keep the tool telling the agent to be careful with them. With that change the right conversation shows up in the top five results for 96% of questions, up from 13%, with no AI model involved in the search at all.

The second thing

With search working, the agent scored about 90%. The whole history scored higher. I wanted to know what was in the gap, so I sorted every wrong answer by how far the evidence got.

On one model, when the agent had opened every note that held the evidence, it was right 131 times out of 133. Fifteen of its nineteen misses were the same mistake: it answered from the little preview snippet in the search results, with the note it needed sitting right there, unopened.

Telling it to open more notes barely helped. Changing the tool did: a search can now return its top three notes in full, so finding and reading are one step.

Checking myself

Here is where it would have been easy to fool myself. If you adjust a tool while watching a set of questions, it gets better at those questions. So before the second fix I split the 500 in half, tried things on one half, wrote down what I was going to run, and only then ran it on the half I had not touched.

On the smaller model Sextant is level with reading everything. On the larger one it is two points behind, which is inside what a sample this size can tell apart from luck. It gets there reading 16 to 40% of the text. On the larger model that is about five and a half cents a question instead of thirty-four.

One caution I owe you. The smaller model scored four points lower on the half I tuned on than on the half I held out. That is noise, and it cuts both ways, so the fair figure for it is both halves together: 91.6%, which is exactly what the whole history scores over the same 500.

The case memory exists for

That benchmark fits inside a model's window. The real argument for memory is the history that does not. A larger version of the same test buries each answer in about 476 conversations, around 1.75 million tokens. You cannot paste that into any of these models. Looking it up is the only option.

There Sextant scores between 81 and 86%, reading two to five percent of the history.

I expected the semantic search option to help at that size. I ran it both ways. It did not help. Most of what is still wrong is one kind of question, where the answer is spread across several conversations and one of them never surfaces.

I had a theory about why. Sextant's semantic index only read the opening of a long note, and a conversation is a long note. So I rebuilt the index to read notes in overlapping passages, which is what most people would call the obvious fix, and tested it on search alone before paying for anything. The right conversation came up first more often. The hard cases did not move at all: three questions gained, three lost, and every search took twice as long. I did not ship it. It is on a branch with the numbers in the commit message, and the theory is filed under wrong.

Two checks before I published

Every number so far is a single run, so I ran four of them again with everything frozen.

Same run, twiceFirstSecond
Larger model, 50 conversations93.6%93.6%
Smaller model, 50 conversations93.6%94.8%
Larger model, 476 conversations85.3%86.5%
Smaller model, 476 conversations84.1%84.9%

The scores came back within about a point. Somewhere between four and nine percent of individual answers flipped each time. That is the ruler for everything on this page. A gap of a point or two is what the same thing does when you run it twice.

Then I handed the code to an independent automated review. It found ten problems, and all ten were real. One had inflated a cost figure for the smaller model. One was a flaw in my first fix: when memory had nothing on a question, Sextant could hand back a note that shared a single common word with it and call that a weak match, where the right answer is "I have nothing on that." Both are fixed, and I re-ran every search afterwards to make sure the fix did not change what gets found. It did not. Then I ran the headline number a third time, on the fixed code. 93.6 again.

I would rather you read that here than find it yourself.

What this does not prove

The grading model here is not the one the benchmark's authors used, so none of these numbers can be set beside anyone else's published score. The baselines were each run once. I am one person with a workstation. What I can say is that every comparison on this page was run on the same questions with the same model, and that the losses are on the page with the wins.

The whole study cost under 200 dollars. The harness, the cost ledger and every result file are in the repository, and the search half reproduces on a laptop with no API key.

How this was made

I ran this study with an AI coding agent, Claude. I chose the question, the benchmark and the budget. I decided to run the baseline that might embarrass the product, to keep the losses in, to split the questions before tuning, and to stop and re-plan when the first result came back at 16%. The agent wrote most of the harness, ran the jobs, did the statistics and drafted this page, and I read, questioned and redirected it throughout.

I think that division of labor is the actual skill now: knowing what to ask for, what to distrust, and when to change course. The numbers are reproducible either way.

Both fixes are in Sextant now. It is free and open source. If you run it and it gets something wrong, I would like to know, because apparently that is how it gets better.

Readers: Claude Haiku 5.5 (smaller) and Claude Sonnet 5.5 (larger). Judge: Claude Opus 5.5 with the benchmark's own grading prompts. Benchmark: LongMemEval, cleaned 2025 release, S and M sets. Corrections to this page are added here with a date.
